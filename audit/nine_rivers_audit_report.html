What I found in your save file

A robot played your game from level 1 to level 25, and then I attacked the file the game uses to remember your progress. The good news is the game itself works. The bad news is that file trusts anything it is handed.

What this actually means for you

Nine Rivers is a single-player game. There is no server holding your players' accounts, so nobody's personal data is at risk here. No passwords, no emails, nothing to leak. That is worth saying plainly before the red text below.

What is at risk is two things you care about commercially:

Money. Your paid items — Remove Ads, Spirit Pearls, the Imperial Gold and Obsidian Ink tile sets — are handed out based on what the save file says. Someone who edits that file gets all of it for free, and the game never double-checks with Google Play. On Android, edited save files get packaged up and shared on modding sites; this is routine, not exotic.

Trust. Separately from any attacker, the save file is fragile. If the phone dies mid-write — battery, force-close, Android killing the app — the file is destroyed and the player silently restarts at level 1 with no backup. That is the kind of thing that produces one-star reviews you cannot answer.

The single most useful fix

Your billing code already asks Google Play "what has this person bought?" on every launch (query_purchases in monetization_manager.gd). Right now it only ever adds items from that answer. If you also remove anything Play does not confirm, the two critical findings below stop being worth anything to an attacker — because a forged file would be corrected within seconds of the game starting.

Findings · 10 checks, ordered by severity

The attacks, one by one

T02 The lock's key is printed inside the app Critical

The save file is locked with a password, and the file is also stamped with a tamper-proof seal. Both the password and the recipe for the seal are written as plain text inside the app itself. Anyone who unzips your APK can read them, so they can open the file, change it, and re-stamp it so it looks untouched.

Proved byReading the two constants out of save_manager.gd, writing a save that grants everything, and signing it with the recipe. The game accepted it without a single warning.
Result
pearls = 9,999,999 jade = 9,999,999 no_ads = true all 4 paid tile sets unlocked integrity check = PASSED
FixYou cannot hide a key inside an app you ship — treat this as unfixable and move the decision elsewhere. Let Google Play be the authority on what was purchased, and accept that the pearl balance is cosmetic.
T03 The seal only covers three numbers Critical

Even if the seal could not be forged, it only protects jade, pearls and the remove-ads flag. Everything else in the file is completely unprotected — and you do not even need the key recipe to change it, because changing it does not break the seal.

Proved byLeaving the three protected numbers at their honest starting values, then rewriting everything else. The seal stayed valid, so no warning fired.
Result
level = 99 daily streak = 365 all 50 levels at 3 stars all 4 paid tile sets unlocked every tile at max mastery (permanent score bonus) all 5 koi unlocked (permanent gameplay bonuses)
FixSign the whole file, not three fields — hash the entire saved payload rather than jade|pearls|no_ads.
T01 The lock is optional — you can just skip it Fixed

Now fixed. The plain-text fallback has been removed. A file that will not unlock is treated as damaged, and the game moves on to its backup copy instead of trusting it. Safe to remove outright because the game has not shipped, so no player has an old unencrypted save to migrate.

When the game cannot unlock the save file, it does not treat that as suspicious. It shrugs, tries reading the file as ordinary text instead, and accepts whatever it finds. So an attacker does not even need the password from T02 — they can hand over a plain, unlocked, unsealed file and the game will take it.

Proved byWriting a plain text file with no encryption and no seal at all.
Result
level = 50 all 50 levels at 3 stars streak shields = 99 ACCEPTED
FixThis fallback exists to migrate players from old unencrypted saves, which is a fair reason — but it should only accept a plain file that still carries a valid whole-file signature, and it should be removed entirely a version or two after launch.
T04 A broken seal is a warning, not a refusal High

When the seal genuinely does fail, the game logs a warning, trims the three protected numbers back down — and then loads the rest of the tampered file anyway. The paid tile sets came through untouched.

Proved bySubmitting a file with a deliberately garbage seal.
Result
correctly clamped: pearls 250, jade 500, no_ads false still applied: level 77 all 4 paid tile sets 2 paid background themes
FixA failed check should reject the file, fall back to the backup copy (see T07), and only then start fresh — never partially apply a file it has already decided is untrustworthy.
T05 A malformed file can permanently break saving Fixed

Now fixed. Every value is checked as it loads and replaced with its default if it is the wrong shape. Finishing a level after loading this exact hostile file now records the stars and pays the jade correctly.

The game never checks that the things in the save file are the right shape. If the list of star ratings arrives as a piece of text instead of a list, the game copies it in as-is. Then the next time the player finishes a level, the save code hits that text, throws an error, and stops halfway through — so the level is never recorded and the jade reward is never paid. It will fail the same way every level, forever.

Proved byLoading a file with wrong types, then calling the real record_level_clear().
Result
SCRIPT ERROR: Nonexistent function 'get' in base 'String' at save_manager.gd:219 (record_level_clear) -> stars not recorded, jade not awarded, file never written SCRIPT ERROR: Trying to assign value of type 'float' to a variable of type 'Array' at monetization_manager.gd:275 (is_theme_unlocked) -> the store stops recognising owned themes
FixCheck the type of each value as it is loaded and fall back to the default when it is wrong. This also protects you from half-written files, which is the same failure without an attacker.
T07 An interrupted save destroys the player's progress Fixed

Now fixed. Saves are written to a scratch file, read back to prove they are complete, and only then swapped in — with the previous version kept as a spare. Re-running this exact attack now recovers the level-25 profile instead of resetting to level 1. Three further crash scenarios were tested and all recover.

This one needs no attacker — just bad luck. The game writes directly over the only copy of the save file. If the phone dies, the player force-closes, or Android kills the app during that write, the file is left half-finished and unreadable. There is no backup, so the next launch starts from scratch. The player loses everything and the game says nothing.

Proved bySaving a real level-25 profile, then cutting the file to 60% of its length to imitate a crash mid-write.
Result
profile before : level 25, 5,000 jade after reload : level 1 (silently reset) backup file : none
FixWrite to a temporary file, close it, then rename it over the real one — a rename is all-or-nothing, so the old file survives any interruption. Keep the previous version as a .bak and fall back to it when the main file will not load. Also check that the file actually opened before writing; right now a failed open is ignored silently.
T06 Impossible numbers are accepted without question Fixed

Now fixed. Money cannot go below zero, levels are held between 1 and 51, and stars between 0 and 3. Unknown tile sets, backgrounds and koi are dropped rather than loaded, so a made-up item id can no longer be injected and equipped.

Negative money, negative levels and four-star ratings all load fine. A negative balance is worse than it sounds: the shop checks "do you have enough?", a negative number never does, and the player can never buy anything again — including with real money.

Proved byLoading a correctly signed file full of out-of-range values.
Result
pearls = -50,000 jade = -100,000 level = -5 stars[1] = 999 (inflates the level-select total) level -5 does not crash: the negative index wraps, so the game quietly deals the hard "Dragon Gate" board as stage -5 instead of the tutorial board.
FixClamp every number to a sane range on load: money at or above zero, level between 1 and 50, stars between 0 and 3.
T08 The upgrade path for future save formats is empty Medium

Saves carry a version number so that a future update can convert old files. The function that is supposed to do that conversion currently just stamps the new version number on and changes nothing. It also does not object to a file claiming to be from a newer version than the app.

Proved byLoading a file stamped version = 99 into the version 2 build.
Result
accepted silently, level = 40
FixNothing is broken today, but the first time you change the save format this will quietly misread every existing player's file. Write the real conversion step when you bump the version, and refuse files newer than the app understands.
T09 Every single tile writes the whole file to storage Fixed

Now fixed. Tile-mastery counts and jade rewards now go through the four-second batch instead of writing immediately. Simulating a full 144-tile board — 288 calls that previously caused 288 writes — now causes zero, and runs in 0.8 ms instead of 53 ms. Finishing a level still saves at once, and purchases still commit the moment the goods are granted.

Proved byTiming 144 consecutive record_tile_mastery() calls.
Result
144 full encrypt-and-write cycles 53 ms on a desktop SSD — considerably slower on phone storage, and a likely stutter source
FixCall request_save() instead of save_game() in these paths. Fewer writes also means fewer chances to be interrupted mid-write, which directly reduces the risk in T07.
T10 The file really is encrypted on disk Passed

The one clean result. The saved file is genuine AES-encrypted binary with no readable text in it, so a curious player poking around with a file browser cannot simply edit their pearl count. That is a real barrier against casual cheating — it is only the determined attacker from T02 who walks past it.

Result
1,052 bytes, no readable field names found

Gameplay bot · Calm Journey, levels 1–25

The bot's run, level by level

The bot drives the real game — it loads main.tscn, reads the board, and taps tiles through the same click handler a finger would. After every level it checks that the save recorded the right level number, the right star rating, and at least the right jade reward. Every one of those checks passed.

Two things worth noting. At level 3 the bot painted itself into a corner and had to restart the board — the board was solvable, but greedy play can still strand it, which is normal for Mahjong solitaire and is exactly what the shuffle button is for. And after saving and reloading, every whole number in the file used to come back as a decimal (26 becoming 26.0), drifting further with each save cycle. That is now fixed by the load validation, and the bot's persistence check passes with zero failures.
